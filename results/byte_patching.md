# Byte patching: decode cost at equal loss (example 07)

`uv run python examples/07_byte_level_patching.py --steps 800` (seq 256, batch 16, constant lr 2e-3, 1 thread,
4-core CPU). Test is the held-out last 10% of the corpus. Decode: batch 1, greedy, 64-byte prompt + 192 new bytes,
4 prompts, every network KV-cached / state-carried (`BLTStream`, `HNetStream`, `LMStream`, tested to match the
parallel forward). Decode bytes/s is the range over two runs on a shared machine; MACs are linear-layer
multiply-accumulates per generated byte (attention scores not counted).

| model | held-out bits/byte | bytes / patch | inner steps / byte | linear MACs / byte | decode bytes/s |
|---|---|---|---|---|---|
| byte transformer (3 x d128) | 2.930 | 1 | 1 | 626k | 1,190-1,680 |
| BLT, entropy patches (published recipe) | 3.428 | 3.03 | 0.198 | 248k | 1,065-1,573 |
| **BLT, space patches (SpaceByte)** | **3.416** | **6.58** | **0.100** | **165k** | **2,582-2,584** |
| H-Net (learned chunks) | 2.834 | 3.23 | 0.073 | 181k | 1,395-1,729 |

Space patches: lower loss than entropy patches with half the latent steps, a third fewer MACs per byte and no
entropy model (one fewer sequential network call per byte), so 1.6-2.4x the decode speed. Matching the entropy
patcher's rate closer to the space rate (`--target-bytes-per-patch 6.5`, 4.9 bytes/patch) did not close the gap.

Tried and dropped:

- **Aligned latent read** (a patch's last byte reads its own just-closed patch, so the next patch's high-entropy
  first byte is predicted from fresh context; a cheap answer to "patch lag"). Same compute, but worse at 800 steps:
  3.456 vs 3.428 (entropy) and 3.460 vs 3.416 (space).
- **H-Net chunk smoothing as one matmul** instead of a loop over chunks: 1.8x faster for that op, but no measurable
  change in an H-Net train step (the Mamba2 recurrence dominates).

- **Multi-byte prediction heads + self-speculative decode** on BLT space patches (Medusa-style heads on the
  local decoder output, trained 1,500 steps on the frozen model so the base loss is unchanged; one parallel
  encoder/decoder pass verifies [next byte, k drafts], exact greedy acceptance, KV / patch / latent rollback,
  latent step deferred until a byte of the next patch needs it). Output was identical to greedy, but slower:

  | k drafts | bytes per verify pass | decode bytes/s (2 runs) |
  |---|---|---|
  | greedy | 1 | 2,418-2,784 |
  | 1 | 1.60 | 2,068-2,576 |
  | 2 | 1.96 | 2,059-2,463 |
  | 3 | 2.18 | 1,816-1,841 |
  | 4 | 2.31 | 1,399-1,463 |

  On one CPU core at this size a step is per-call overhead, not weight traffic: a 3-byte verify pass costs about
  1.5-2x a 1-byte step, and heads that only see the decoder state accept about one extra byte. It should pay
  off where a step is weight-bandwidth bound (a much larger local decoder, or GPU), or with better drafts.

- **BLT-S self-speculation** (Fast BLT, Kallini et al. 2026, arXiv:2605.08044), as the paper describes it: the
  local decoder drafts k bytes past patch boundaries reading the last available latent output (no latent step),
  then one pass verifies [next byte, drafts] with the full model, all patches the window closes going through
  the latent in one call; exact greedy match, rollback of KV / patch / latent state. Output identical to greedy.
  Drafts are accepted often and latent calls drop a lot, but wall time is worse. Medians of 5 interleaved
  rounds, 8 prompts x 192 bytes; latent calls over 4 prompts including prompt prefill:

  | model | greedy bytes/s | k=4 | k=8 | k=16 | bytes per pass (k=4 / 8 / 16) | latent calls (greedy -> k=16) |
  |---|---|---|---|---|---|---|
  | BLT space patches | 2,698 | 2,109 | 2,068 | 1,989 | 4.9 / 8.3 / 13.7 | 104 -> 56 |
  | BLT entropy patches | 1,383 | 1,291 | 1,279 | 1,150 | 4.7 / 7.5 / 11.5 | 307 -> 71 |

  BLT-S saves global-model (latent) calls, but every byte still pays for sequential local encoder and decoder
  steps while drafting, and the verify pass adds a parallel decoder pass. Here the latent is a small part of a
  decode step (2 x d128 layers once per 6.6 bytes, next to 1 + 1 x d64 local layers every byte), and space
  patching already halved its calls, so there is little left to save. Fast BLT's gains (up to 77% less memory
  traffic) are for models whose global transformer dominates the cost.

Kept, same outputs, less wasted work:

- Patch pooling as a segment softmax (each byte scores only against its own patch's query) instead of a dense
  (patches x bytes) attention mask: BLT forward 84 -> 76 ms (16 x 256 bytes), train step 163 -> 153 ms.
- The max-patch cap vectorized (forced starts at multiples of max_patch from each natural start) instead of a Python
  loop over bytes: 3.0 -> 0.1 ms per 16 x 256 batch.

Single seed; small models; CPU timings are call-overhead bound, so MACs and inner steps per byte are the
portable numbers.
